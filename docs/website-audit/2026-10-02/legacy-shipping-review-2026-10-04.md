## 核心结论

旧脚本的实际业务顺序是：

**管理订单打开“确认发货”页并保留窗口 → 国内仓分拣 → 国内仓打包 → 国内仓立即发货 → 查发货记录取得运单 → 回到原确认页填写物流信息并最终确认。**

1. 先点击管理订单中的 `goConfirmShipment` 控件，是打开确认发货页面、读取买家国家并保存窗口；旧脚本没有在这一阶段点击最终提交（978–1014 行）。
2. 仓库步骤发生在最终提交之前（1046–1059 行）。
3. 获取仓库运单后，才回到确认窗口填写并点击 `input.btnConfirmDeliverGoods`（1063–1124 行）。
4. 本轮现场操作支持上述先后关系。不能把“管理订单先点发货/打开确认页”误记为“此时已最终完成卖家发货”。打开页面是否另有隐含后端副作用，仍需请求及状态读回证据确认。

## 本轮现场确认对旧代码的修正

### 当前 V2 两侧物流下拉框使用同一套 value

| 物流 | 旧运费模块返回的中间码 | 当前 V2 国内仓库 value | 当前 V2 卖家回填 value |
| --- | --- | --- | --- |
| 中邮 | `20004` | `10001` | `10001` |
| E 邮宝 | `20002` | `10002` | `10002` |
| 燕文 | `20003` | `10003` | `10003` |
| UPS | `20001` | `20001` | `20001` |

- 本轮现场已确认上表两个 V2 下拉框的 value 一致。
- `20002`、`20003`、`20004` 是旧运费模块和旧脚本之间传递的中间码，**不是当前 V2 页面 value**。
- 旧主脚本在仓库按显示名称选择物流，并非向仓库直接填写上述旧中间码（824–827 行）；在卖家确认页另做中间码转换（635–644 行）。因此，不能由旧常量推断旧仓库或当前仓库的真实 option value。
- 旧名称映射位于 101–107 行；旧运费模块返回码位于运费模块 23–28、356–361 行。V2 接口实现应保留当前页面/接口实测的物流 ID，并将旧中间码兼容转换限制在清楚命名的适配边界。

### 订单关联不能使用两侧 SKU 展示文本

- 本轮同一测试订单在国内仓库显示的 SKU 与卖家页面子 SKU 不同，但订单 ID 一致。
- 这已足以否定“用两侧 SKU 展示文本直接串接同一订单”的假设。
- 当前可用线索是两侧一致的订单 ID；其具体请求字段名、作用域、是否还需订单行 ID，以及多商品/拆包场景下的关联关系仍待验证。
- 不应进一步推断“展示产品编号”“仓库 SKU”“卖家子 SKU”三者同义。本文不记录这次测试订单或 SKU 的原始值。

### 仓库选行与确认弹窗的细节

分拣、打包的选行 XPath 模板（526 行）：

```xpath
//tr[.//span[contains(text(), '产品编号：')]/following-sibling::span[contains(text(), '{product_id}')]]//input[contains(@class, 'subcheck')]
```

立即发货使用同类产品编号匹配（817–822 行）。发货记录使用相同产品编号匹配后读取第 4 列（872 行）。这些都是旧实现线索，不是 V2 中可直接采用的订单关联契约。

- 分拣/打包动作后，脚本先尝试在对应 iframe 内找 `input[value='确定']`，再尝试顶层 Kendo 窗口中的同名按钮（552–565 行）。
- 库存不足仅靠文本包含“库存是否不足”识别（567–583 行）。
- 普通确认后还会尝试对原确认按钮再次点击（585–591 行），之后按 iframe title 关闭弹窗并切回仓库主 frame（608–620 行）。
- 仓库立即发货函数没有采用上述分拣/打包的确认处理流程；动作点击后就尝试关闭窗口（829–841 行）。现场必须单独确认这一步实际提示、请求完成和业务状态变化。

### V2 应按业务边界分别采集

1. 管理订单列表读取：分页、状态筛选、订单/订单行 ID、数量、SKU/产品字段和未发货统计。
2. 打开确认发货页：导航请求与附随数据请求；记录打开前后状态，判断是否仅准备页面。
3. 分拣：待分拣列表读取、选中实体的真实 ID、提交请求、返回结果与后续状态读回。
4. 打包：待打包列表、提交对象、包裹/订单关系、结果读回。
5. 仓库立即发货：待发货列表、选中实体 ID、当前物流 value、提交请求、发货结果与费用/库存影响。
6. 发货记录查询：订单 ID、记录 ID、物流 ID、运单、时间、包裹维度及筛选/排序规则。
7. 卖家最终确认：订单/订单行 ID、服务、承运人、运单、响应判定，以及提交后的订单状态和运单读回。

每一步应保存脱敏后的请求方法/路由/字段结构、响应业务标识、前后状态证据，以及它和前一步的关联键；成功提示或 HTTP 200 单独不足以证明订单完成。捕获不等于授权重放，修改型调用应沿当前用户授权的单单流程执行。

### 运费直接依赖的额外假设

- 模块说明声称先定位表头再按精确列名查找，但实际加载使用固定表头行和固定列索引；`find_header_row` 定义在运费模块 79–92 行，未被实际加载流程使用（96–251、303–339 行）。
- UPS 按向上取整的整数公斤计费，只加载/处理 1–20 kg；注释中的“四舍五入”与实际 `ROUND_CEILING` 不同（运费模块 96–107、258–265 行）。
- E 邮宝默认上限 2 kg；以色列特殊上限判断依赖规则名称中的中文，但规则名称来自英文国家列，应作为待核对缺陷而非已验证支持（运费模块 142、151、269–272 行）。
- 燕文/中邮统一限制不超过 2 kg，按 0.15/0.3/2.0 kg 分档，缺失阶梯价格时回退前档，并假定单价单位为元/kg、固定费用为元/单（运费模块 276–298 行）。
- 模块声明移除货代服务费、仅计算基础运费（运费模块 3–8 行）；并不证明当前 V2 的实际扣费口径一致。
- 上述仅为静态代码假设/风险。本次没有以运费工作簿内容或现场实际扣费完成验证。

## 当前可采用结论与未完成项

可采用：

- 流程应区分打开确认页与最终确认；仓库发货、取得运单发生在最终卖家确认之前。
- 当前 V2 国内仓库与卖家物流下拉 value 统一为中邮 `10001`、E 邮宝 `10002`、燕文 `10003`、UPS `20001`。
- 两侧 SKU 展示可不同，不能用其直接串接订单；应继续验证共同订单 ID 及订单行/包裹关联。
- 旧脚本适合作为流程和控件线索，不构成 V2 API 契约、幂等策略或业务成功证明。

仍需完成：

- 为每个读写动作补齐实测 API 方法、路由、字段及响应语义。
- 明确订单、订单行、仓库任务、包裹、发货记录的 ID 关系与状态迁移。
- 验证当前物流值在实际提交请求中的字段名及类型，不能仅因 DOM value 相同而假定所有接口字段同名。
- 验证数量/库存/费用/运单的实际变更和最终卖家状态，覆盖“仓库成功但回填失败”的恢复分支。
- 对多商品、同 SKU 多订单、部分缺货、重复打开/提交及记录延迟建立安全验证方案；本文不代表这些边界已获现场验证。
