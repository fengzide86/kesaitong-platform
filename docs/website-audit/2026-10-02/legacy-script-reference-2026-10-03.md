## 与 V2 现场页面的优先对照

### 物流模板（历史首轮快照；后续写入结果见专门章节）

- 旧脚本目标是 `SellerShippingTemplateSetting`，现场账户设置页也显示“配送设置”入口。首次静态盘点时没有进入保存表单；后续授权现场已创建 `Smart_Precise_V34_0.15kg` 并回读列表，详情见 `script-sync-complete-2026-10-03.md`。
- 需要先只读核对：入口是否仍可达、运输服务类型、国家选择、重量/价格字段、模板列表和读取请求；保存/更新按钮继续禁止点击。
- 旧脚本选择了国际服务代码 `20001` 等内部值，这些值不能直接当成 V2 评分或业务规则。

### 商品与广告（历史首轮快照；后续写入结果见专门章节）

- 两个广告脚本都先进入库存管理；V7.1 在 FBA 筛选行读取 SKU/ASIN/价格，V5.4 先读普通库存父级 SKU，再从 FBA 行读取 ASIN/价格，再进入广告/促销分支。
- 首轮现场只观察到库存页首屏、筛选控件和读取请求；后续授权实测已完成商品推广、优惠券、购买折扣、FBA 转换和 Prime 保存，详情见专门章节，不代表旧脚本可直接复用。
- 现场看到的广告活动、秒杀、优惠券、Prime 折扣和促销入口属于旧脚本核心范围；截图明确排除的是数据报告分区里的“广告”入口、早期评论者计划及其它报告页。**报告入口排除，不等于广告活动主流程排除。**
- 旧脚本会填写并提交活动/促销内容；“本轮只做字段和状态对照”是首轮历史快照，不能覆盖后续授权实测。旧脚本点击日志仍不等于业务结果回读。

### 订单、国内仓库与 FBA

- 旧发货主脚本不是只读脚本：会进入订单、国内仓库 iframe，执行分拣、打包、立即发货、物流选择和最终确认，并回读发货记录。
- V2 现场订单页已经确认订单筛选、状态计数、配送类型和列表读取接口；FBA“只转换”已完成并回读库存，但未创建货件；国内仓库分拣/打包/发货仍未作为可执行能力验收。
- 后续应先建立“订单行 → 商品详情重量 → 物流报价 → 发货表单 → 回读记录”的只读证据链，不把旧脚本的点击成功当作当前 V2 可用。

## 本地运费表结构（只读）

`FreightTemplate_v2.xlsx` 包含 4 个工作表：

1. `中国邮政挂号小包`：国家/地区、0–150g、151–300g、301g–2000g 的配送费与挂号服务费。
2. `e邮宝`：国家/地区、起重、按克计重的重量资费、包裹操作处理费，并含部分国家限重说明。
3. `燕文航空挂号小包`：国家/地区代码、1–150g、151–300g、301–2000g 三段配送服务费与 Item 服务费。
4. `ups 全球快捷`：国家、1–20kg 阶梯、44/70/99/299/499/999/9999kg 等大重量段；备注说明体积重按长×宽×高/5000，并且报价不含燃油费。

旧模块的核心计算关系是“国家别名归一化 → 重量/体积重 → 可用渠道与限重过滤 → 价格阶梯 → 最优渠道/报价”；具体数值与平台显示仍需现场回读核对。

## 网络与兼容性结论

- 代码中没有发现 `requests`、`httpx` 或直接 REST 客户端；网络请求主要由 Selenium 浏览器在导航、XHR、iframe 和提交按钮操作时产生。
- 旧脚本使用 `www.idtrade.cn` 登录入口、课程参数、iframe class、页面英文/中文文本和大量 XPath/CSS 选择器；当前 V2 现场主机为 `www.bjysoft.cn`，即使路径同名也不能直接复用。
- 旧脚本没有统一的请求记录、幂等键或提交后回读契约；新系统接入时应先做只读预检、字段定位和结果回读，再逐个开放写入动作。
- 原脚本自带 `chromedriver-win64`、`.venv`、`__pycache__`，这些是运行环境/缓存，不作为产品脚本能力或 Git 交付内容。
- 旧目录 `.venv\Scripts\python.exe` 仍无法启动，报错指向已不存在的基础 Python 路径；本轮只在 `D:\AmazonToolboxData\venvs\legacy-script-audit` 创建了独立 Python 3.12 环境，用于本地运费离线测试，没有安装 Selenium、没有启动浏览器，也没有运行平台自动化脚本。

## 本地运费逻辑离线复跑

- 已在独立的 D 盘 Python 3.12 审计环境中运行 `物流比价测试脚本.py`；没有启动浏览器、没有访问外部平台、没有写回 Excel。
- `FreightTemplate_v2.xlsx` 成功读取 4 个工作表，共汇总 749 个国家/地区别名记录；0.1kg、0.5kg、2.5kg 三档计算均完成。
- 2.5kg 档大部分结果按脚本预期切换到 UPS；重点国家抽查也输出 UPS 结果，说明“超过小包重量后切换渠道”的本地算法路径可运行。
- 结果同时暴露数据清洗风险：报表前部出现 `nan` 国家名和同一国家多别名重复行，说明当前 Excel 读取层还需要去空值、别名去重和国家规范化后再作为页面输入。
- 这些是本地运费表的计算事实，不代表 V2 平台当前评分规则、实时运费或账号页面数据；浏览器脚本仍未执行。

## 平台脚本运行尝试结论

- 旧平台自动化脚本本轮没有直接执行：它们一旦进入主循环就会创建营销对象、修改物流模板或确认发货，且发货脚本是持续轮询，不是一次性验收命令。
- 运行前检查确认旧脚本使用 `www.idtrade.cn` 和旧选择器，而当前登录站点是 `www.bjysoft.cn:8732`；即使补齐 Selenium 依赖，也不能把“跑起来”当作 V2 成功。
- 可继续安全推进的方式是：使用当前已登录浏览器逐页复现旧脚本的读取前置步骤，捕获页面和只读网络；对创建/保存/发货按钮先停在提交前，除非明确指定单个测试对象、时间、预算和回滚方式。

## 当前结论

旧脚本最值得参考的是四条业务主线：物流模板、商品/库存读取、广告/促销字段、订单到发货回读。截图中明确排除的应用商店、绩效、数据报告、品牌店、增长和账户辅助入口不进入这些主线。下一步只对照旧脚本实际使用的页面与 V2 现场结构，不直接执行旧脚本。
